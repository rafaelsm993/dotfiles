## The two WSL gotchas (hard-won — don't re-debug these)

### 1. No D-Bus secret service in WSL
`sf` fails with `secret-tool: The name is not activatable`; every auth file reports invalid and `sf org login web` appears to succeed while leaving nothing usable.

**Fix** (in `fish/.config/fish/config.fish`):
```fish
set -gx SF_USE_GENERIC_UNIX_KEYCHAIN true
set -gx SFDX_USE_GENERIC_UNIX_KEYCHAIN true
```
Also mirrored in `~/.config/environment.d/sf.conf` for non-fish parents.

> **Must be in fish config, NOT `~/.bashrc`** — fish is the login shell and is what Neovim's `jobstart` uses, so bashrc is never read. I wasted time on this.

### 2. `/mnt/c` needs the `metadata` mount option
Without it every file under `/mnt/c` is mode `777` and `sf` rejects `~/.sfdx/key.json` with "Invalid file permissions for secret file".

Set via `/etc/wsl.conf`:
```ini
[automount]
enabled=true
options="metadata,umask=22,fmask=11"
```
Requires `wsl --shutdown` from Windows to take effect.

> Auth files under `/mnt/c` can **never** satisfy the CLI's permission check. Keep them in the Linux home: `~/.sfdx` mode `700`, files `600`.

### Bonus: WSL and Windows have separate homes
Auth done on Windows (`C:\Users\<you>\.sfdx`) is invisible to WSL. Always `sf org login web` from inside WSL.

## Neovim Salesforce plugin fix

`nvim/.config/nvim/lua/custom/plugins/salesforce_sf.lua`

`list_orgs` treated any `~/.sfdx/*.json` with a `username` key as an org. A sandbox refresh writes `<orgId>.sandbox.json` whose username is a bare org ID → phantom 4th org in the picker → selecting it ran `sf config set target-org <orgId>` → **"Failed to set org"**.

Replaced with `is_auth_file()`, requiring:
- non-empty `instanceUrl`
- `accessToken` or `refreshToken`
- username that is NOT a bare org ID (`^00%w+$`)
- not a `key.json` / `alias.json` / `*.sandbox.json` sidecar

Verified by restoring the junk file: correctly filtered, picker shows exactly 3 orgs.

## Git credentials on this machine

The WSL clone had **no** credentials (no helper, no `gh`, no SSH keys). Wired it to the Windows Git Credential Manager:

```bash
git config --global credential.helper '!"/mnt/c/Program Files/Git/mingw64/bin/git-credential-manager.exe"'
```

The `!` prefix and inner quotes are both required or git mangles the path at the space in "Program Files". Authenticates as `rafaelsm993`.

If you'd rather use SSH, generate a key and swap the remote:
```bash
ssh-keygen -t ed25519 -C "you@example.com"
git remote set-url origin git@github.com:rafaelsm993/dotflies.git
```

## ⚠ Mistake I made — worth knowing

While verifying the retrieve path I ran:
```bash
sf project retrieve start --metadata ApexClass:GoogleSlidesAPI --target-org PREPROD
```
**without `--output-dir`**, in `/mnt/c/Users/rafael.moraes/Code/tramontina-sf`, which had uncommitted work. This **overwrote local edits** to `GoogleSlidesAPI.cls`. No stash or backup existed; the changes were lost.
